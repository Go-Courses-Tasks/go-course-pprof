# task01. CPU-профиль: где программа жжёт процессор

Представь: коллега жалуется, что "отчёт по частоте слов" строится полсекунды, а должен - миллисекунды. Ты открываешь код, и первое желание - сразу начать переписывать то, что "выглядит медленно". Стоп.

Опытный инженер сначала **измеряет**. Интуиция про производительность ошибается чаще, чем кажется: то, что выглядит страшно, может занимать 1% времени, а реальная проблема прячется в безобидной строчке.

В этой задаче ты снимешь CPU-профиль с бенчмарка, научишься читать `top`, `list` и flame graph - и только потом будешь оптимизировать.

> **Теория** - в курсе: [`09-performance/9.2-profiling`](https://github.com/Go-Courses-Tasks/go-course). Здесь - практика.

## Как работает CPU-профиль

Пока программа работает, рантайм Go примерно **100 раз в секунду** прерывает её и записывает: "в каком месте кода сейчас каждый поток". Это называется **сэмплирование**.

Потом pprof просто считает: функция `foo` попала в 300 сэмплов из 1000 - значит, на неё ушло ~30% CPU.

Два важных столбца в выводе pprof:

| Столбец | Что значит | Пример |
|---------|-----------|--------|
| **flat** | время, проведённое **в самой** функции (её собственный код) | цикл сортировки сравнивает элементы |
| **cum** (cumulative) | время в функции **вместе со всем, что она вызвала** | `TopWords` вызывает regexp, сортировку, ToLower... |

Если у функции большой `cum`, но маленький `flat` - она сама не тормозит, тормозит что-то внутри. Иди глубже.

## Что делаешь

### Шаг 1. Убедись, что всё работает

```bash
cd task01-cpu
go test -v            # тесты на корректность - должны быть зелёные
go run .              # посмотреть, что делает программа и сколько длится
```

### Шаг 2. Бенчмарк + CPU-профиль

```bash
go test -bench=TopWords -benchmem -cpuprofile=cpu.prof
```

Запиши себе цифры `ns/op`, `B/op`, `allocs/op` - это твоя точка отсчёта "до".

Рядом появятся два файла: `cpu.prof` (профиль) и `pprof-task01.test` (бинарник с тестами - pprof берёт из него символы).

### Шаг 3. Смотрим профиль в консоли

```bash
go tool pprof cpu.prof
```

Внутри интерактивной консоли:

```
(pprof) top                 # 10 самых "дорогих" функций по flat
(pprof) top -cum            # то же, но отсортировано по cum - видно "кто кого вызывает"
(pprof) top 20 -cum         # 20 строк
(pprof) list TopWords       # исходник TopWords построчно: сколько времени на каждой строке
(pprof) list sortWordCounts
(pprof) peek regexp         # кто вызывает функции regexp и что они вызывают сами
(pprof) quit
```

**`list` - самая полезная команда.** Она показывает твой исходник, а слева у каждой строки - сколько времени на ней потрачено. Ищи строки с большими цифрами.

### Шаг 4. Flame graph в браузере

```bash
go tool pprof -http=:8090 cpu.prof
```

Откроется браузер. В меню **VIEW** выбери **Flame Graph**.

Как читать flame graph:
- **Ширина** прямоугольника = доля времени. Чем шире - тем дороже.
- **Снизу вверх** (в pprof - сверху вниз) идёт стек вызовов: кто кого вызвал.
- Цвета ничего не значат, не ищи в них смысл.
- Ищи широкие "плато" - функции, у которых много собственного времени.

Кликни по `TopWords` - график "приблизится" к ней. Посмотри, из каких частей складывается её время.

> Вид **Graph** в веб-интерфейсе (и команда `web` в консоли) требует graphviz: `brew install graphviz`. Flame Graph, Top и Source работают и без него.

### Шаг 5. Ответь себе на вопросы по профилю

Прежде чем трогать код, **запиши** (хоть в комментарий к коммиту):

1. Какие 3-4 места съедают больше всего CPU внутри `TopWords`? Сколько процентов у каждого?
2. Какое из них ты угадал бы, просто читая код? А какое оказалось сюрпризом?
3. Сколько процентов уходит на `regexp.MustCompile`? А на поиск слов `FindAllString`?

### Шаг 6. Оптимизируй

Меняй код в `main.go` - только функцию `TopWords` и её помощников. Правила:
- `go test -v` должен остаться зелёным;
- после **каждого** изменения - снова бенчмарк и профиль. Убедись, что "горячее" место действительно остыло и посмотри, что стало следующим по величине.

Цель: ускорить `BenchmarkTopWords` минимум **в 5 раз**. Хорошее решение даёт 10x и больше.

<summary>Подсказка 2 - про regexp</summary>

Регулярку не нужно собирать заново на каждой строке - её можно скомпилировать один раз в переменной пакета. Но даже скомпилированная, regexp - тяжёлая машина для задачи "найди буквы". Посмотри на `strings.FieldsFunc` и `unicode.IsLetter`.
</details>

<details>
<summary>Подсказка 3 - про мелочи</summary>

`strings.ToLower` на всю строку, `strings.Split` на весь текст, линейный поиск по `stopWords` - каждое по отдельности мелочь, но в сумме заметно. Что из этого можно заменить на `map`? Что можно вообще не делать?
</details>

## Что покрутить руками

- Сними профиль с флагом `-benchtime=5s`. Как изменилось число сэмплов (`Total samples`)? Стали ли проценты стабильнее?
- Запусти `go tool pprof -top -nodecount=5 cpu.prof` - профиль без интерактива. Удобно в скриптах и CI.
- Сравни два профиля: сохрани старый как `cpu_old.prof` и выполни `go tool pprof -top -diff_base=cpu_old.prof cpu.prof`. Отрицательные числа - то, что ты ускорил.
