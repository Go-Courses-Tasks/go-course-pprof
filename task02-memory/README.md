# task02. Профиль памяти: кто аллоцирует и зачем

Сервис отчётов работает "нормально", но в метриках странное: CPU занят наполовину сборщиком мусора, а `go_memstats_alloc_bytes_total` растёт с бешеной скоростью. Код при этом простой - распарсить CSV и склеить строки.

Проблема Go-сервисов чаще всего не в "медленном алгоритме", а в **лишних аллокациях**. Каждая аллокация на куче - это работа для аллокатора сейчас и работа для GC потом. Миллион мелких аллокаций в секунду может съесть больше CPU, чем сама бизнес-логика.

В этой задаче ты снимешь профиль памяти, разберёшься в разнице между `alloc_space` и `alloc_objects` и уберёшь лишнее.

> **Теория** - в курсе: [`09-performance/9.2-profiling`](https://github.com/Go-Courses-Tasks/go-course) и [`9.3-memory`](https://github.com/Go-Courses-Tasks/go-course). Здесь - практика.

---

## Четыре взгляда на один профиль памяти

Файл `mem.prof` (он же heap-профиль) хранит сразу **четыре** набора чисел. Переключаются они флагом `-sample_index`:

| sample_index | Что показывает | Когда смотреть |
|--------------|----------------|----------------|
| `alloc_space` | сколько **байт** выделено за всё время | "кто гоняет больше всего памяти через аллокатор" |
| `alloc_objects` | сколько **объектов** выделено за всё время | "кто больше всего нагружает GC мелочью" |
| `inuse_space` | сколько байт **живёт прямо сейчас** | утечки памяти, растущий RSS |
| `inuse_objects` | сколько объектов живёт прямо сейчас | то же, в штуках |

Для бенчмарков почти всегда интересны `alloc_*`: всё, что функция выделила, она потом выбросила, и `inuse` будет почти пустым. А `inuse_*` пригодится в task03, где мы будем ловить утечку в живом сервисе.

**Почему байты и объекты - разные картины?** Одна аллокация на 1 МБ и миллион аллокаций по 1 байту дают одинаковый `alloc_space`, но совершенно разную нагрузку на GC. Смотри на оба.

## Что делаешь

### Шаг 1. Тесты и точка отсчёта

```bash
cd task02-memory
go test -v
go test -bench=. -benchmem
```

Запиши `ns/op`, `B/op` и `allocs/op` для обоих бенчмарков. Посмотри на `B/op` у `RenderReport`: отчёт весит ~300 КБ. Сколько байт на него выделяется? Во сколько раз больше?

### Шаг 2. Снимаем профиль памяти

Снимай профиль **по одному бенчмарку за раз** - иначе бенчмарки с разным числом итераций перемешаются, и проценты будет сложно читать:

```bash
go test -bench=RenderReport -benchmem -memprofile=render.prof
go test -bench=ParseOrders  -benchmem -memprofile=parse.prof
```

> По умолчанию рантайм записывает в профиль в среднем одну аллокацию на каждые 512 КБ. При `-memprofile` `go test` можно попросить писать каждую: добавь `-memprofilerate=1`. Точнее, но медленнее.

### Шаг 3. Байты: `alloc_space`

```bash
go tool pprof -sample_index=alloc_space render.prof
```

```
(pprof) top
(pprof) list RenderReport
```

Найди строку, на которую приходится почти вся память. Подумай: почему склейка строк, которые в сумме весят 300 КБ, выделяет сотни мегабайт?

### Шаг 4. Объекты: `alloc_objects`

```bash
go tool pprof -sample_index=alloc_objects parse.prof
```

```
(pprof) top
(pprof) list ParseOrders
```

Здесь картина другая: байт немного, но **штук** - десятки тысяч на один вызов. Найди каждую строку, которая аллоцирует, и для каждой ответь: эта аллокация нужна? Её можно избежать или сделать одну вместо многих?

Попробуй и в браузере - там удобно переключать `SAMPLE` прямо в меню:

```bash
go tool pprof -http=:8090 parse.prof
```

### Шаг 5. Спроси у компилятора

Часть аллокаций - это переменные, которые "убежали" на кучу (escape analysis). Компилятор может рассказать, что и почему убегает:

```bash
go build -gcflags='-m' . 2>&1 | grep main.go
```

Ищи строки `escapes to heap` и `moved to heap`.

### Шаг 6. Оптимизируй

Меняй `ParseOrders` и `RenderReport`. Тесты должны остаться зелёными.

Цели:
- `RenderReport`: `B/op` - не больше чем ~2x от размера итогового отчёта, время - в десятки раз меньше;
- `ParseOrders`: `allocs/op` - хотя бы в 2 раза меньше.

После каждого изменения - снова бенчмарк и профиль.

## Подсказки

<details>
<summary>Подсказка 1 - склейка строк</summary>

Строки в Go неизменяемые. `report += line` каждый раз создаёт **новую** строку длиной "всё, что было, плюс line" и копирует туда всё. Для N строк это O(N²) байт. Есть `strings.Builder` - и у него есть `Grow`, если знаешь примерный итоговый размер.
</details>

<details>
<summary>Подсказка 2 - fmt.Sprintf</summary>

`fmt.Sprintf` удобен, но аллоцирует строку-результат и упаковывает аргументы в `interface{}`. Писать в `strings.Builder` можно напрямую: `WriteString`, `strconv.AppendInt`, `strconv.AppendFloat`. А `fmt.Sprintf("%s", s)` - это просто дорогая копия `s`.
</details>

<details>
<summary>Подсказка 3 - слайсы</summary>

`var orders []Order` + `append` в цикле - слайс несколько раз перевыделяется и копируется по мере роста. Если знаешь верхнюю границу размера (`len(lines)`), задай capacity сразу: `make([]Order, 0, len(lines))`. То же с `items`. А для разбивки на фиксированное число частей есть `strings.SplitN`, `strings.Cut`.
</details>

## Что покрутить руками

- Запусти `GODEBUG=gctrace=1 go run .` - сколько раз отработал GC до и после оптимизации?
- Сними профиль `-memprofilerate=1` и сравни с обычным. Сильно ли поменялись проценты? Почему в проде так никто не делает?
- Сравни профили до/после: `go tool pprof -sample_index=alloc_space -top -diff_base=render_old.prof render.prof`.

## Вопросы на подумать

1. Чем `alloc_space` отличается от `inuse_space`? Почему в профиле бенчмарка `inuse_space` почти пустой?
2. Почему `report += line` в цикле - это O(N²) по памяти, хотя каждая строка маленькая?
3. Функция выделяет 2 МБ за вызов одним куском, другая - 2 МБ по 16 байт. Что хуже для GC и почему?
4. Профиль памяти по умолчанию - сэмплирующий (раз в 512 КБ). Может ли редкая мелкая аллокация вообще не попасть в профиль? Что тогда поможет её найти?
