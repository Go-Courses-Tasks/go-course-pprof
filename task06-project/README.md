# task06. Финальный проект: найди и исправь бутылочное горлышко

Это задача "как на работе". Тебе не скажут, где проблема. Есть функция, есть бенчмарк, есть жалоба: "отчёт по access-логу строится слишком долго, раньше успевал за минуту, теперь нет". И есть всё, чему ты научился в task01-task05.

А ещё на работе мало сказать "я ускорил". Нужно **доказать**: показать цифры до и после, причём такие, которым можно верить. Для этого в Go есть `benchstat`.

> **Теория** - в курсе: [`09-performance/9.1-benchmarks`](https://github.com/Go-Courses-Tasks/go-course) и [`9.2-profiling`](https://github.com/Go-Courses-Tasks/go-course). Здесь - практика.

## Что делает код

`Analyze` в [`analyzer.go`](./analyzer.go) принимает строки access-лога:

```
2026-10-23T10:00:00Z GET /api/users/42 200 15ms
```

и считает по каждому эндпоинту (числовые сегменты пути заменяются на `:id`) число запросов, число 5xx и p95 латентности.

```bash
cd task06-project
go run .        # отчёт по сгенерированному логу на 20 000 строк
go test -v      # тесты, включая "золотой": отчёт должен совпадать байт в байт
```

## Почему нельзя просто сравнить два запуска

Запустил бенчмарк - 180 ms. Поменял код, запустил - 165 ms. Ускорил на 8%? Не факт. Запусти ещё раз старую версию - может, будет 165. Браузер в фоне, турбобуст процессора, GC в неудачный момент - шум легко бывает 5-10%.

`benchstat` берёт **много** прогонов каждой версии и говорит:
- медиану и разброс (`± 3%`);
- изменение (`-91.87%`);
- **статистическую значимость** (`p=0.002`). Если `p` большой или стоит `~` - разница неотличима от шума, хвастаться нечем.

Установка:

```bash
go install golang.org/x/perf/cmd/benchstat@latest
# или без установки: go run golang.org/x/perf/cmd/benchstat@latest old.txt new.txt
```

## Что делаешь

### Шаг 1. Зафиксируй "до"

```bash
go test -run='^$' -bench=Analyze -benchmem -count=10 | tee old.txt
```

`-count=10` - десять независимых прогонов. Пока идёт - не трогай ноутбук, закрой тяжёлые вкладки. И **не закоммить** `old.txt` раньше времени - он тебе понадобится в конце (в `.gitignore` он есть, но приложи вывод benchstat в PR).

### Шаг 2. Профили

Сними оба профиля одним прогоном:

```bash
go test -run='^$' -bench=Analyze -benchmem -cpuprofile=cpu.prof -memprofile=mem.prof
```

И разбери их всем, что умеешь:

```bash
go tool pprof -top -cum cpu.prof | head -30
go tool pprof -http=:8090 cpu.prof
go tool pprof -sample_index=alloc_space mem.prof
go tool pprof -sample_index=alloc_objects mem.prof
```

```
(pprof) list Analyze
(pprof) list normalizePath
```

> **macOS.** На маке CPU-профиль бывает "шумным": сверху оказываются `runtime.kevent`, `runtime.pthread_cond_wait`, `runtime.usleep` и прочий рантайм. Это особенность того, как macOS доставляет сигналы профилировщика, а не твой код. Сузь профиль до своей функции:
>
> ```bash
> go tool pprof -top -cum -focus=Analyze -relative_percentages cpu.prof
> ```
>
> Теперь проценты считаются от времени внутри `Analyze`. Во flame graph то же самое - просто кликни по `Analyze`.

### Шаг 3. Составь список подозреваемых

**До** того как править код, выпиши в описание PR таблицу:

| # | Где (функция:строка) | % CPU (cum) | % alloc_space | Почему медленно | Как исправить |
|---|---------------------|-------------|---------------|-----------------|---------------|
| 1 | ... | ... | ... | ... | ... |

Проблем несколько, и они разного рода: что-то видно в CPU, что-то - в памяти, а что-то - как `runtime.gcBgMarkWorker` и `runtime.mallocgc` в CPU-профиле. Подумай: откуда в CPU-профиле сборщик мусора и чья это "вина"?

### Шаг 4. Исправляй по одной

Правило хорошего оптимизатора: **одно изменение - один замер**. Иначе не поймёшь, что сработало, а что было зря.

Для каждой проблемы:

```bash
# поправил одно место
go test -v                                                          # результат не изменился?
go test -run='^$' -bench=Analyze -benchmem -count=10 | tee new.txt
benchstat old.txt new.txt                                          # стало лучше? значимо?
```

Если изменение не дало значимого результата - откати его. Код, который "наверное быстрее", но не доказано, - это просто усложнение.

### Шаг 5. Итог

Цели:
- `sec/op` - быстрее минимум в **10 раз**;
- `B/op` - меньше минимум в **20 раз**;
- все тесты зелёные, `TestAnalyzeGolden` в том числе.

Финальное сравнение:

```bash
go test -run='^$' -bench=Analyze -benchmem -count=10 > new.txt
benchstat old.txt new.txt
```

Вывод `benchstat` и таблицу из шага 3 - в описание PR.

## Подсказки

<details>
<summary>Подсказка 1 - где искать</summary>

Посмотри на каждую строку внутри цикла `for _, line := range lines` и спроси себя: "это нужно делать на **каждой** строке? это нужно делать **так**?" Цикл крутится 20 000 раз - любая лишняя работа умножается на 20 000.
</details>

<details>
<summary>Подсказка 2 - инструменты стандартной библиотеки</summary>

`fmt.Sscanf` и `fmt.Sprintf` - универсальные, но медленные: рефлексия, `interface{}`, аллокации. Для фиксированного формата хватит `strings.Fields` / `strings.Cut` и `strconv.Atoi`, а строки склеиваются через `+`.

`regexp.MustCompile` - это компиляция регулярки. Её делают один раз, в переменной пакета. А для "заменить числовые сегменты пути" регулярка вообще не обязательна.
</details>

<details>
<summary>Подсказка 3 - про insertSorted</summary>

Нам нужен p95 только **в конце**. Нужно ли держать слайс отсортированным после каждой вставки? И сколько памяти выделяет `insertSorted` на один вызов, если в слайсе уже 2 000 элементов?
</details>

## Что покрутить руками

- Попробуй `go test -bench=Analyze -benchmem -count=10 -cpu=1,4,8`. Зависит ли скорость от числа ядер? Почему (вспомни про GC)?
- Запусти бенчмарк с `GOGC=off` до и после оптимизации. Насколько изменилось время "до"? Это и есть цена мусора.
- Сравни профили до и после: `go tool pprof -top -diff_base=cpu_old.prof cpu.prof`.
- Включи PGO (Profile-Guided Optimization): положи CPU-профиль рядом как `default.pgo` и прогони бенчмарк ещё раз. Дал ли компилятор что-то бесплатно?
