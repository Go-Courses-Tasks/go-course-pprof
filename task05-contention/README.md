# task05. Block и mutex профили: где горутины ждут

Классическая история: сервис упёрся в производительность, его переносят на машину с 16 ядрами вместо 4 - и RPS не меняется. CPU загружен на 20%. Снимаешь CPU-профиль - он почти пустой, ничего "горячего" нет.

Потому что горутины **не работают - они ждут**. Стоят в очереди за мьютексом или висят на отправке в канал, который не успевают читать. CPU-профиль показывает, где тратится процессор. А ожидание процессор не тратит - его CPU-профиль не видит.

Для этого в Go есть ещё два профиля:
- **block** - где горутины **блокировались** (мьютексы, каналы, `select`, `WaitGroup.Wait`, `Cond.Wait`) и сколько суммарно прождали;
- **mutex** - где **держали** мьютекс, пока за ним стояла очередь (contention).

> **Теория** - в курсе: [`09-performance/9.2-profiling`](https://github.com/Go-Courses-Tasks/go-course). Здесь - практика.

---

## Block vs Mutex: в чём разница

Они похожи, но смотрят с разных сторон:

| | block | mutex |
|---|-------|-------|
| Чья точка зрения | того, **кто ждёт** | того, **кто держит** и мешает |
| Где покажет стек | на `Lock()`, `<-ch`, `ch <-`, `Wait()` | на `Unlock()` - в момент освобождения рантайм знает, сколько за этим мьютексом прождали |
| Что видит | мьютексы **и** каналы, select, WaitGroup, Cond | только мьютексы (`sync.Mutex`, `sync.RWMutex`) |
| Включение в коде | `runtime.SetBlockProfileRate(n)` | `runtime.SetMutexProfileFraction(n)` |
| Включение в `go test` | `-blockprofile=block.prof` (сам выставит rate=1) | `-mutexprofile=mutex.prof` (сам выставит fraction=1) |

По умолчанию оба **выключены**: у них есть оверхед. В живом сервисе их включают явно, обычно не на каждое событие, а с семплированием (например, `SetMutexProfileFraction(100)`), и снимают через `/debug/pprof/block` и `/debug/pprof/mutex`.

## Что делаешь

### Шаг 1. Тесты и точка отсчёта

```bash
cd task05-contention
go test -race -v
go run .
go test -run='^$' -bench=. -cpu=1,2,4,8
```

`-run='^$'` - не запускать тесты, только бенчмарки. `-cpu=1,2,4,8` - прогнать параллельный бенчмарк с разным GOMAXPROCS.

Посмотри на `BenchmarkGetParallel` с разным числом ядер. `ns/op` в параллельном бенчмарке - это "время на операцию с учётом параллельности". Если бы всё масштабировалось идеально, на 8 ядрах было бы в 8 раз меньше, чем на 1. Что видишь ты?

### Шаг 2. Сначала - CPU-профиль (и убедись, что он мало что говорит)

```bash
go test -run='^$' -bench=Parallel -cpuprofile=cpu.prof
go tool pprof -top cpu.prof | head -20
```

Сколько CPU занимает собственно работа (`sha256`)? Видно ли из этого профиля, **почему** 8 ядер не дают ускорения?

### Шаг 3. Block-профиль

```bash
go test -run='^$' -bench=Parallel -blockprofile=block.prof
go tool pprof block.prof
```

```
(pprof) top
(pprof) top -cum
(pprof) list Get
```

Числа здесь - **не** CPU, а **суммарное время ожидания** всех горутин. Оно может быть во много раз больше длительности бенчмарка: 8 горутин, каждая прождала 1 секунду = 8 секунд.

Найди в `list Get` две строки, на которых горутины ждут. Для каждой ответь: **чего** ждём и **кто** держит?

> В `top` будет и `sync.(*WaitGroup).Wait`, и `runtime.chanrecv1` из кода самого фреймворка бенчмарков - это нормальное ожидание, игнорируй. Смотри на то, что вызывается из `Get`.

### Шаг 4. Mutex-профиль

```bash
go test -run='^$' -bench=Parallel -mutexprofile=mutex.prof
go tool pprof mutex.prof
```

```
(pprof) top
(pprof) list Get
```

Время записано на строке `Unlock` (у нас - на `defer s.mu.Unlock()`). Это значит: **пока Get держал мьютекс**, остальные стояли в очереди столько-то. Теперь посмотри, что именно делается **под** этим мьютексом. Всё ли это нужно делать под ним?

Flame graph тоже работает: `go tool pprof -http=:8090 block.prof`.

### Шаг 5. Исправь

Меняй `Service` в `main.go`. Правила:
- `go test -race -v` должен остаться зелёным (поведение `Get`, `Stats`, `Close` не меняется: каждый `Get` попадает в аудит, `Close` возвращает точное число);
- `BenchmarkGetParallel` должен ускориться **минимум в 2 раза**;
- после исправления снова сними block- и mutex-профили и убедись, что время ожидания в `Get` сократилось в разы.

## Подсказки

<details>
<summary>Подсказка 1 - что делается под мьютексом</summary>

Правило: под мьютексом делаем только то, что **обязано** быть атомарным - чтение/запись общей map и счётчиков. Всё долгое - вычисления, I/O, отправку в каналы - выноси наружу. `defer s.mu.Unlock()` удобен, но держит мьютекс до самого конца функции.
</details>

<details>
<summary>Подсказка 2 - про канал events</summary>

Канал небуферизованный, а читатель у него один и делает работу на каждое событие. Значит, каждый `Get` ждёт, пока аудитор доделает предыдущее событие. Варианты: буфер у канала, несколько аудиторов (тогда счётчик `audited` должен стать атомарным), пачки событий.
</details>

<details>
<summary>Подсказка 3 - если хочется ещё быстрее</summary>

Один мьютекс на весь кэш - сам по себе бутылочное горлышко. Посмотри на `sync.RWMutex` (большинство запросов - чтение), на шардирование (N кусков map, у каждого свой мьютекс) и на `atomic` для счётчиков.
</details>

## Вопросы на подумать

1. Почему CPU-профиль не показывает ожидание на мьютексе? Что он показывает, когда горутина спит в `Lock()`?
2. В block-профиле ожидание - 12 секунд, а бенчмарк шёл 1 секунду. Как такое возможно?
3. Почему mutex-профиль показывает стек на `Unlock`, а не на `Lock`?
4. Зачем в проде ставят `SetMutexProfileFraction(100)`, а не `1`? Что потеряешь?
5. Может ли буфер у канала полностью решить проблему, если аудитор в среднем медленнее, чем приходят события?
