# task03. pprof в живом сервисе: `net/http/pprof`

Бенчмарки - это хорошо, но в проде у тебя нет бенчмарка. Есть сервис, который в 3 часа ночи начал есть 400% CPU, и память, которая за сутки доросла до лимита контейнера. Перезапускать и "воспроизводить локально" - долго, а проблема может не воспроизвестись.

Поэтому почти в каждый Go-сервис добавляют одну строчку:

```go
import _ "net/http/pprof"
```

И после этого с **работающего** сервиса можно снять CPU-профиль, heap, список горутин - без перезапуска, без отладчика, прямо по HTTP.

В этой задаче у тебя "сервис авторизации" с двумя проблемами. Найди обе с помощью pprof - и только потом загляни в код.

> **Теория** - в курсе: [`09-performance/9.2-profiling`](https://github.com/Go-Courses-Tasks/go-course). Здесь - практика.

---

## Какие эндпоинты появляются

Открой http://localhost:6060/debug/pprof/ - там список. Главные:

| Эндпоинт | Что это | Как снимать |
|----------|---------|-------------|
| `/debug/pprof/profile?seconds=N` | CPU-профиль: сервис N секунд сэмплируется, потом отдаёт файл | `go tool pprof <url>` |
| `/debug/pprof/heap` | память: что живёт в куче (`inuse_*`) и что выделялось (`alloc_*`) | `go tool pprof <url>` |
| `/debug/pprof/allocs` | тот же профиль, но по умолчанию в режиме `alloc_space` | `go tool pprof <url>` |
| `/debug/pprof/goroutine` | стеки всех горутин | `?debug=1` или `?debug=2` в браузере |
| `/debug/pprof/block`, `/mutex` | блокировки и мьютексы (по умолчанию выключены) | см. task05 |
| `/debug/pprof/trace?seconds=N` | трейс выполнения (не pprof, а `go tool trace`) | `curl -o trace.out <url>` |

**Важно:** CPU-профиль снимается **за время**. Если в эти N секунд сервис простаивает - профиль будет пустой. Поэтому нагрузка нужна **во время** снятия.

## Что делаешь

### Шаг 1. Запусти сервис и нагрузку

```bash
cd task03-http-pprof

# терминал 1 - сервис
go run .

# терминал 2 - проверим руками
curl -X POST "localhost:8081/login?user=bob&password=secret"
curl localhost:8081/stats
```

Генератор нагрузки лежит рядом, в `cmd/load` (можно и `hey`, если стоит):

```bash
# терминал 2 - нагрузка на 60 секунд
go run ./cmd/load -d 60s
```

### Шаг 2. Проблема №1 - CPU

Пока идёт нагрузка, в **третьем** терминале:

```bash
go tool pprof "http://localhost:6060/debug/pprof/profile?seconds=10"
```

pprof 10 секунд ждёт, потом открывает консоль. Профиль заодно сохраняется в `~/pprof/` - путь будет в выводе.

```
(pprof) top
(pprof) top -cum
(pprof) list hashPassword
```

Или сразу в браузере с flame graph:

```bash
go tool pprof -http=:8090 "http://localhost:6060/debug/pprof/profile?seconds=10"
```

Ответь себе:
- В каком нашем хендлере и какой нашей функции проводится почти всё время?
- Почему в `top` по `flat` первыми идут функции из `crypto/...`, а не наши? Что тогда покажет `top -cum`?
- Это **баг** или **так и задумано**? (Подумай про то, зачем пароли хешируют медленно.)

### Шаг 3. Проблема №2 - память

Посмотри несколько раз на `/stats` во время нагрузки и после неё:

```bash
curl localhost:8081/stats
```

`heap_inuse` растёт и **не падает**, даже когда нагрузка закончилась и GC отработал. Это утечка. Найдём, кто держит память:

```bash
go tool pprof -sample_index=inuse_space http://localhost:6060/debug/pprof/heap
```

```
(pprof) top
(pprof) list newSession
```

`inuse_space` - это то, что **живо прямо сейчас**. Если функция много выделяет и всё сразу выбрасывает - её тут не будет. Если она тут сверху - значит, кто-то держит ссылку на выделенное.

### Шаг 4. Сравни два снимка кучи

Самый надёжный способ доказать утечку - сравнить "до" и "после":

```bash
curl -s -o heap1.prof http://localhost:6060/debug/pprof/heap
go run ./cmd/load -d 20s
curl -s -o heap2.prof http://localhost:6060/debug/pprof/heap

go tool pprof -sample_index=inuse_space -top -diff_base=heap1.prof heap2.prof
```

В выводе останется только то, что **прибавилось** между снимками.

### Шаг 5. Исправь

1. **CPU.** Хеширование пароля дорогое специально, но 50 000 раундов SHA-256 на каждый логин - перебор для учебного стенда. Подумай, как бы ты ограничил его влияние на сервис (меньше раундов? кэш? лимит параллельных логинов?). Поменяй и докажи профилем, что доля `hashPassword` упала, а RPS вырос.
2. **Память.** Сессии живут вечно. Добавь им время жизни: например, фоновую горутину, которая раз в N секунд удаляет сессии старше TTL. Заодно подумай, нужен ли сессии буфер `Payload` заранее.

После исправления прогони нагрузку 60 секунд и убедись, что `heap_inuse` в `/stats` держится на одном уровне, а в `inuse_space` нет `newSession` на первом месте.

## Подсказки

<details>
<summary>Подсказка - почему GC не помогает</summary>

GC освобождает только то, на что **никто не ссылается**. Глобальная `map` `sessions` ссылается на каждую сессию, а сессия - на свой `Payload`. Пока запись есть в map - память живая, и GC её не тронет. Утечки памяти в Go почти всегда выглядят так: что-то долгоживущее (глобальная map, кэш, слайс) копит ссылки.
</details>

## Что покрутить руками

- Открой в браузере http://localhost:6060/debug/pprof/goroutine?debug=1 под нагрузкой и без. Сколько горутин держит HTTP-сервер на каждое соединение?
- Сними трейс: `curl -o trace.out "http://localhost:6060/debug/pprof/trace?seconds=3"` и открой `go tool trace trace.out`. Найди там GC-паузы.
- Сними `allocs` вместо `heap`: `go tool pprof http://localhost:6060/debug/pprof/allocs`. Чем картина отличается от `inuse_space`?
- Перенеси pprof на основной mux (`mux.Handle("/debug/pprof/", ...)`) и подумай, почему так в проде делать не стоит.

2. CPU-профиль сняли за 10 секунд при 8 ядрах. Почему `Total samples` может показать больше 10 секунд?
3. Чем `inuse_space` отличается от `alloc_space`? Какой из них показывает утечку, а какой - "кто больше всех мусорит"?
4. Сколько стоит держать `import _ "net/http/pprof"` в проде, если профили никто не снимает? А во время снятия CPU-профиля?
